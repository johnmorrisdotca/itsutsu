# `releasedIn` backfill — the mapping, and what could not be mapped

Generated by `node --env-file=.env scripts/derive-released-in.ts`. The rules are
`src/lib/backlog/releasedInBackfill.ts`, which is pure and unit-tested;
`scripts/backfill-released-in.ts` is what applies a `certain` row, on somebody's word.

## What was read

- **156** rows on the board read, **61** of them done.
- **61** done rows carry no `releasedIn` — the working set.
- **200** releases in `CHANGELOG.md`, and **215** versions
  in git's `package.json` history, each with the instant it was bumped.

## What came out

| | rows |
|---|---|
| certain — what `--run` would write | 11 |
| likely — for a person to confirm | 1 |

Only `certain` is ever written. A `likely` or a `possible` is in the JSON so it
can be read and judged, and `scripts/backfill-released-in.ts` skips both.

## There is no door for this yet

Nothing above the database can stamp a row that is already `done`, and that was
measured rather than assumed — a probe against `backlogStore.ts` with Prisma mocked:

- `finishItem` is the only writer `releasedIn` has ever had, and it refuses
  anything that is not `inProgress`: *"Only a row in progress may be marked done;
  this one is "done"."*
- `changeItem` takes no such field. A `PATCH` carrying `releasedIn` and no
  `status` reaches it, the field lands in the `...edit` rest, `editProblems` has
  no opinion on it, and the write it composes is `{}`. The call returns
  `ok: true` and the row is unchanged — **the API answers 200 and stamps
  nothing.**

So a backfill that trusted that 200 would report every row stamped and stamp none.
`scripts/backfill-released-in.ts` re-reads each row it writes and stops on the
first one that did not take, rather than counting successes it cannot see.

**The addition that opens it** — a change to the board's contract, so it wants the
operator's word rather than a script's:

1. `backlogStore.ts`: a `stampRelease(id, release, actor)` beside `finishItem`,
   writing `releasedIn`/`releasedAt` and nothing else onto a row that is already
   `done` and unstamped. Not a move — no `status`, no `movedAt`, no claim — so
   BOARD_RULES.md invariant 1 ("a done row does not move") and 9 ("the release
   tool writes `done`") both still hold: it grants no new way to REACH done.
   Refuse a row that is not done, and refuse one already stamped, so a release
   that has been stated can never be rewritten.
2. `src/app/api/backlog/[id]/route.ts`: before the `status === done` branch, route
   a body carrying `releasedIn`/`releasedAt` and NO `status` to `stampRelease`,
   token actors only, with the `SEMVER` and date checks the done branch makes.

Until that lands, `pnpm board:released-in` is a report.
